# PRD 评估清单

对 `docs/prd.md`（或同等命名：`PRD.md` / `prd.md`）逐节评估。

## 0. 文件级检查

| # | 检查项 | 是/否/部分 | 严重度 |
|---|---|---|---|
| 0.1 | 文件存在且 ≥ 50 行 | | critical（< 50 行基本是占位） |
| 0.2 | 顶部有"最后更新"日期 | | nice-to-have |
| 0.3 | 有清晰的一句话"产品愿景 / What"陈述 | | critical |

---

## 1. §1 愿景

| # | 检查项 | 是/否/部分 | 严重度 |
|---|---|---|---|
| 1.1 | **一句话能讲清**产品是什么 + 给谁用 + 解决什么问题 | | critical |
| 1.2 | 含可识别的痛点（不是"提升效率"这种空话） | | important |
| 1.3 | 不超过 3 句话 | | nice-to-have（写得长通常是堆 features） |

**坏愿景示例**：

```
❌ "打造一站式开发者协作平台，赋能团队高效创新"
   → 空话：没有任何具体场景
```

**好愿景示例**：

```
✅ "重度刷 GitHub 的开发者需要一个本地可备份、
   按多维分类、带私人笔记的仓库收藏工具，
   数据完全在自己的 git 仓库里。"
```

---

## 2. §2 目标

| # | 检查项 | 是/否/部分 | 严重度 |
|---|---|---|---|
| 2.1 | **3-7 条**，太多 = 没目标，太少 = 没想法 | | important |
| 2.2 | 每条都是 **可验收** 的（"30 秒内自动入库"✅；"体验流畅"❌） | | critical |
| 2.3 | 含可度量指标（数字 / 时间 / 阈值），不只是形容词 | | important |
| 2.4 | 不混目标和方法（"用 React + Next.js" 不是目标） | | important |

**反模式**：

```
❌ "提供良好的用户体验" → 没度量
❌ "支持 10000+ 用户" → 跟"个人知识库"产品定位矛盾（要先确认是不是这个目标）
❌ "集成 AI 能力" → 方法不是目标
```

---

## 3. §3 非目标 ⚠️ 最常缺失

| # | 检查项 | 是/否/部分 | 严重度 |
|---|---|---|---|
| 3.1 | **存在** §3 非目标（这是 PRD 最易缺失的一节） | | critical |
| 3.2 | 列出 **3+ 条** 明确"不做"的事 | | critical |
| 3.3 | 每条都带"为什么不做的原因"（不只是断言） | | important |
| 3.4 | 非目标不是"v2 再做"那种模糊项（那是 §6） | | important |

**为什么 critical**：没有 §3 的 PRD 几乎必然导致范围蔓延。每次有人提"能不能加 X"，没有 §3 就只能凭感觉拒。

**好非目标示例**：

```
✅ "不做多用户 / 多设备同步 / 协作编辑（v1 是个人单设备工具）"
✅ "不做云端 SaaS（数据完全本地）"
```

---

## 4. §4 核心用户场景

| # | 检查项 | 是/否/部分 | 严重度 |
|---|---|---|---|
| 4.1 | **3-5 个**具体场景 | | important |
| 4.2 | 每个场景用 agile 三段式或类似的 user story 格式 | | important |
| 4.3 | 场景描述**具体动作**（"粘贴 URL 添加 repo"✅；"管理知识"❌） | | important |
| 4.4 | 场景覆盖核心用户路径（不能只描述边角） | | critical |

---

## 5. §5 数据模型（速查）

| # | 检查项 | 是/否/部分 | 严重度 |
|---|---|---|---|
| 5.1 | 含核心实体清单（不是完整 schema） | | important |
| 5.2 | 标注**字段归属**（哪个字段属于哪个来源 / 谁写） | | important |
| 5.3 | 不重复 ADD 里的详细 schema | | nice-to-have |
| 5.4 | 与 §2 / §4 场景对应（数据模型能解释场景需要什么） | | important |

---

## 6. §6 范围外 (v1 不做)

| # | 检查项 | 是/否/部分 | 严重度 |
|---|---|---|---|
| 6.1 | 与 §3 非目标**不重复**（§3 = 不做，§6 = v2 候选） | | critical |
| 6.2 | 列了**未来候选**，有理由放到 v2 | | nice-to-have |

**§3 vs §6 的区分**：

| | §3 非目标 | §6 范围外 (v2) |
|---|---|---|
| 含义 | 永远不做 | v1 不做，v2 考虑 |
| 例 | "不做多用户协作" | "v2 加跨设备同步" |
| 区分价值 | 防止被反复要求加 | 防止 v2 计划彻底失忆 |

---

## 7. §7 里程碑现状

| # | 检查项 | 是/否/部分 | 严重度 |
|---|---|---|---|
| 7.1 | **存在** §7 里程碑现状 | | critical（缺失 = 不知道项目进行到哪） |
| 7.2 | 表格形式（里程碑 / 完成度 / 状态） | | important |
| 7.3 | 状态客观（不夸大，不全 ✓ 假装都做完了） | | critical |
| 7.4 | 与 `sprint.md §1` Sprint / Version 一致(不能两边对不上) | | critical |

---

## 8. §8 成功指标 (定性)

| # | 检查项 | 是/否/部分 | 严重度 |
|---|---|---|---|
| 8.1 | 列出 **3-5 条** 可验证指标 | | important |
| 8.2 | 区分**性能** / **体验** / **数据完整性** 等维度 | | nice-to-have |
| 8.3 | 至少 1 条涉及数据完整性（备份 / 恢复 / 原子性） | | important |

---

## 9. §9 风险与缓解

| # | 检查项 | 是/否/部分 | 严重度 |
|---|---|---|---|
| 9.1 | **存在** §9 风险章节 | | important |
| 9.2 | 列出 **3+ 条** 具体风险（不是"可能有问题"） | | important |
| 9.3 | 每条风险有"缓解方案"（不只是识别问题） | | important |

---

## PRD 综合判定

| critical 数 | important 数 | verdict |
|---|---|---|
| 0 | ≤ 2 | **PASS** |
| 0 | ≥ 3 | **FIX** |
| ≥ 1 | 任意 | **REWRITE** |

**最常见的 3 个 PRD 问题**：

1. **缺 §3 非目标**——这是 PRD 最关键的章节，缺失直接 critical
2. **§2 目标写得像 feature list**（"支持搜索" / "支持标签"）——目标是验收标准不是功能
3. **§7 里程碑现状跟代码现实脱节**——文档说 100% 但 git log 显示只到 70%

## 10. 跨文档引用一致性(cross-doc)

> PRD 不是孤立的。它引用 `docs/add.md` 的 ADR、引用 `docs/tasks.md` 的 UC/IF。
> 任何引用不一致 = 文档间失同步,**必须**修。

| # | 检查项 | 命令 / 方法 | 严重度 |
|---|---|---|---|
| 10.1 | **PRD §4 UC 编号跟 tasks.md §1.1 UC 编号一致**(都用 `UC-mm-nn` 双数字业务分组格式) | `grep '^### UC-' docs/prd.md` 跟 `docs/tasks.md` 比对 | critical |
| 10.2 | **PRD §7 Milestone/Sprint 代号跟 `sprint.md §1` Sprint 代号一致** | `grep 'Sprint\|M[0-9]' docs/prd.md` 跟 `docs/sprint.md §1` 比对 | critical |
| 10.3 | **PRD §6 范围外每条引用 `sprint.md §2` Product Backlog 编号**(`UC-NN-NN [P3]` 或 `TB.N`) | `grep 'TB\.\|UC-[0-9]' docs/prd.md` 看是否每条 6-x 都有引用 | important |
| 10.4 | **PRD §1 引用 add.md ADR 编号时,add.md §7 存在对应 ADR** | `grep 'ADR-[0-9]' docs/prd.md` 验证每个引用都在 `docs/add.md` | important |
| 10.5 | **PRD 跟 tasks.md 的 agile 三段式用同一种语言**(都中文 "作为/我希望/以便" 或都英文 "As a/I want/So that") | 人工抽检 2-3 条 | important |
| 10.6 | **PRD §3 决策依赖(D-1 ~ D-N)跟 tasks.md §3 决策一致** | 比对两份文档决策表 | important |
| 10.7 | **PRD 不出现技术实现细节**(端口 / 文件路径 / 框架名)— 这些是 add.md 职责 | `grep -E 'FastAPI\|uvicorn\|pnpm\|port' docs/prd.md` ≤ 2(只允许 §1 提品牌名) | important |

## 11. 内容质量加严(基于实际改造经验)

> 这些是 v1 没强调但实际改造时反复出现的质量问题。

| # | 检查项 | 严重度 |
|---|---|---|
| 11.1 | **§2 SMART 目标含 [P0/P1/P2/P3] 优先级标** — 让 stakeholder 一眼看出哪些先做 | nice-to-have |
| 11.2 | **§8 成功指标必须含"数据完整性"维度** — 备份/恢复/原子性/状态机正确性 ≥ 1 条 | important |
| 11.3 | **§1 愿景有"30 秒复述检验"段** — 拿掉 §1 后,新人能否复述 3 句产品定位 | nice-to-have |
| 11.4 | **§4 UC 不要跟 tasks.md §1.1 UC 内容重复**(PRD 高层摘要即可,完整 UC 在 tasks) | important |
| 11.5 | **§1 顶部有"文档定位"段** — 明确"PRD 是契约,tasks 是执行,add 是实现",避免读者找错文件 | nice-to-have |
